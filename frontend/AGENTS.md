# AGENTS.md

Frontend for the FlagLab CTF platform: React 19 + **TanStack Start** (SSR, file-based TanStack Router) on Vite, TypeScript, deployed to Vercel. The backend lives in the sibling `backend/` folder — the API contract is `backend/frontendPrompt.md` + `backend/openapi.json`, and backend internals are in `backend/AGENTS.md`. This file covers `frontend/` only.

## Commands

Run from `frontend/`:

```bash
npm install
npm run dev        # vite dev (Vite default port 5173)
npm run build      # vite build -> .output/ (.vercel, nitro preset)
npm run preview    # serve the production build
npm run lint       # eslint . (no --fix; can be slow)
npm run format     # prettier --write .
```

- **There is no test runner** — don't invent `npm test`.
- **`npm run build` does NOT typecheck.** Run `npx tsc --noEmit` as the real type gate. TS is strict with `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noUncheckedSideEffectImports` — these are the flags that will actually bite you.
- Both `bun.lock`/`bunfig.toml` and `package-lock.json` are committed (package manager is ambiguous). Prefer `npm` unless the user says otherwise.

## Stack

- **Framework:** TanStack Start + TanStack Router (file-based routes), React 19, Vite 8, Nitro (build).
- **Server state:** TanStack Query (`QueryClient` created in `src/router.tsx`, passed via router context).
- **Client state:** Zustand — only `src/lib/auth-store.ts` today.
- **HTTP:** Axios, wrapped in `src/lib/api-client.ts`.
- **UI:** Tailwind CSS v4 + shadcn/ui (new-york style, slate base) over Radix primitives; `lucide-react` icons; `sonner` toasts; `recharts` charts.
- **Forms/validation:** react-hook-form + `@hookform/resolvers` + Zod.
- **Markdown:** `react-markdown` + `remark-gfm` + `remark-breaks` (challenge descriptions, notes).

## Layout

- `src/routes/` — file-based routes (see Routing below). `src/routeTree.gen.ts` is generated from them.
- `src/api/` — typed backend calls per resource: `auth.ts`, `events.ts`, `teams.ts`, `challenges.ts`, `user.ts`, shared shapes in `types.ts`.
- `src/lib/` — `api-client.ts` (axios + interceptors), `auth-store.ts` (Zustand session), `download.ts` (blob download for signed challenge files), `format.ts`, `utils.ts` (`cn`), `error-capture.ts` / `error-page.ts` (SSR error wrapper), `lovable-error-reporting.ts`.
- `src/components/` — app components; `src/components/ui/` is the shadcn/ui kit (generated — prefer the CLI over hand-editing).
- `src/server.ts` — SSR entry wrapper. **Do not remove:** it converts h3-swallowed SSR failures (`{"unhandled":true,"message":"HTTPError"}`) into a rendered error page, which `try/catch` alone cannot catch.

## Fragile files — don't "fix" these

- **`vite.config.ts` plugin list.** `@lovable.dev/vite-tanstack-config` already wires TanStack devtools, `tanstackStart`, `viteReact`, Tailwind, `tsConfigPaths`, Nitro, `VITE_*` injection, the `@` alias, and dedupe. Adding any of them manually breaks the build with duplicates.
- **`nitro: { preset: "vercel" }`** is deliberate — the Lovable default target emits a Cloudflare Worker bundle that Vercel cannot run.
- **`src/routeTree.gen.ts`** is auto-generated by the router plugin on dev/build — never hand-edit.
- **`emit: server entry` → `src/server.ts`** typing in `vite.config.ts` is intentional (SSR error wrapper).

## Environment & deployment

- One variable: **`VITE_API_URL`** — the backend base URL, **no trailing slash** (dev value in the gitignored `.env`; template in `.env.example`). Set the production value in the **Vercel dashboard**, not a committed file.
- Anything not prefixed `VITE_` is not exposed to client code.
- Deployed to Vercel via Nitro; the backend's CORS origin is the backend's own `FRONTEND_URL` var — if cross-origin calls fail, fix the backend env var, not the client.

## API conventions

- **All HTTP goes through `src/lib/api-client.ts`.** Never create a second axios instance or use bare `fetch` for API calls (the one intentional exception is `download.ts`, which must fetch the signed URL with `credentials: "include"`).
- The instance sets `withCredentials: true`, injects `Authorization: Bearer <access_token>` from the store, and on `401` performs a single-flight `POST /auth/refresh` (cookie-based) and replays the request. If refresh fails it clears the session and redirects to `/login`. Don't add a competing retry/refresh path.
- Add new resource calls under `src/api/<resource>.ts` with explicit request/response types; keep `src/api/types.ts` in sync with `backend/openapi.json`.
- Surface backend messages verbatim with the helpers: `apiErrorMessage(error)`, `apiStatus(error)`, `isInformationalResponse(error)`, `apiMessage(data)`, `asList(data)`.
- **Not every 4xx is a bug.** A wrong flag is a `201` with `status: "WRONG"` (user feedback, not an error), and some `4xx` are expected informational states (e.g. "Event did not start yet.") — use `isInformationalResponse` so they don't render as failures.

## Auth & session

- `src/lib/auth-store.ts` (Zustand) is the **only** place the access token is persisted — `localStorage` keys `ctf.access_token` / `ctf.user`. Call `hydrate()` on boot (see `__root.tsx` / `_app`); `authTokens` is a non-reactive accessor for the interceptors.
- The **refresh token is an httpOnly cookie** — never read, store, or send it from JS. Same for `reset_token` and `google_link_token`.
- Auth is cookie + bearer both: `withCredentials: true` must stay on for refresh/OAuth/password-reset to work.
- Gate authed pages with `src/components/require-auth.tsx` (plus the `_app.*` route shell), not ad-hoc checks.

## Routing conventions

File-based: every `.tsx` in `src/routes/` is a route. Do **not** create `src/pages/`, `src/routes/_app/index.tsx`, or `app/layout.tsx` (Next.js/Remix habits). `__root.tsx` is the only root layout and must keep its `<Outlet />`.

| File | URL |
| --- | --- |
| `index.tsx` | `/` |
| `about.tsx` | `/about` |
| `users/index.tsx` | `/users` |
| `users/$id.tsx` | `/users/:id` (dynamic — bare `$`, no braces) |
| `files/$.tsx` | `/files/*` (splat — read via `_splat`, never `*`) |
| `_layout.tsx` | layout route (renders `<Outlet />`) |
| `__root.tsx` | app shell wrapping every page |

In this app, `_app.tsx` is the authenticated shell (nav/footer + `hydrate()`), and `_app.*` files are its children (`_app.events.$eventId.challenges.tsx`, etc.). Non-authed pages (`login.tsx`, `register.tsx`, `verify-email.tsx`, `forgot-password.tsx`, `reset-password.tsx`, `google*.tsx`) sit at the top level. Set page title/meta per route via the route's `head` (`{ title: "..." }`, `{ name|property, content }`) — see `login.tsx` for the pattern.

## UI conventions

- Import primitives from `@/components/ui/*`; add new ones with the shadcn CLI (`components.json` is configured: new-york, slate, `@/components` + `@/lib/utils` aliases) rather than hand-rolling.
- Styling is **Tailwind v4 via `src/styles.css`** (CSS-first: `@import "tailwindcss"`, theme tokens in CSS). There is **no `tailwind.config.js`** — don't create one.
- Use the `@/` path alias (`tsconfig.json` `paths`); avoid deep relative chains.
- Prefer existing shared pieces: `app-shell.tsx`, `auth-layout.tsx`, `ui-states.tsx` (loading/empty/error), `challenge-card.tsx`, `challenge-modal.tsx`, `event-card.tsx`, `event-nav.tsx`, `markdown-content.tsx`, `markdown-editor.tsx`, `join-by-code.tsx`.

## Known gotchas

- **ESLint's `no-restricted-imports` bans `server-only`** — TanStack Start doesn't use the Next.js package. Name server modules `*.server.ts` or mark them `@tanstack/react-start/server-only`.
- `react-refresh/only-export-components` is a warning; route files exporting non-components are tolerated but keep component files clean.
- `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`); a brand-new package version will refuse to install until it ages, with per-package bypasses listed there — confirm with the user before adding to that list.
- `.lovable/` (`plan.md`, `plan/`, `project.json`) is Lovable tooling metadata — don't treat it as product source or edit it as documentation.
- The backend's email-OTP/refresh/OAuth flows are documented in `backend/frontendPrompt.md`; when the two disagree, the backend code wins — update `frontendPrompt.md`.
